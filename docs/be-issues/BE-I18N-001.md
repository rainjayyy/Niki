## 背景

后端目前所有错误 `message` 字段都是写死的中文字符串，
国际化推进到第二语言（英语）的成本巨大：

> 前端要做双语，需要把 `error` CODE 翻译成 message；如果后端能
> 根据 `Accept-Language` 直接渲染，前端只负责切换 UI 文案，
> 错误文案是零成本的。

实际痛点：

- §6.3 错误响应规范要求 `message` 是可读的提示文本，不是 CODE；
- 海外测试团队反馈：英文客户端遇到 `INVALID_PHONE_FORMAT` 时
  看到的还是中文，没法用；
- 文案改一处就要翻前端的 React 文案，跨端不同步。

本工单为后端补上一个零依赖的轻量翻译框架，让同一份错误响应
可以根据 `Accept-Language` 渲染 zh / en 文案。

## 设计

### 1. 包结构

```
niki/i18n/
├── __init__.py          # 公共 API（get_translator / set_translator / t）
├── messages.py          # MESSAGES_ZH / MESSAGES_EN / CATALOGS
├── translator.py        # Translator / pick_lang / DEFAULT_LANG
└── middleware.py        # LanguageMiddleware（BaseHTTPMiddleware）

niki/api/_i18n.py        # 处理器辅助：localized_error_response(...)
```

### 2. Translator

```python
class Translator:
    def translate(
        self, key: str, lang: str | None = None, *, default: str | None = None
    ) -> str:
        # 1) lang 目录命中 → 返回
        # 2) 否则回退 FALLBACK_LANG（en）
        # 3) 否则 default（若提供）
        # 4) 否则返回 key 本身
```

- 单例通过 `get_translator()` / `set_translator()` 暴露
- `DEFAULT_LANG = "zh"`（中文优先，是中文产品）
- `FALLBACK_LANG = "en"`
- 线程安全（catalog 是只读的）

### 3. LanguageMiddleware

```python
app.add_middleware(LanguageMiddleware)

class LanguageMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        lang = pick_lang(
            accept_language=request.headers.get("accept-language"),
            query_lang=request.query_params.get("lang"),
            supported=("zh", "en"),
            default="zh",
        )
        request.state.lang = lang
        response = await call_next(request)
        response.headers["Content-Language"] = lang
        response.headers["Vary"] = "Accept-Language"
        return response
```

`pick_lang` 解析 `Accept-Language` 时按 `q=` 质量值降序排列，
支持 `zh-CN` → `zh` 的 region 折叠；`?lang=` 优先级最高。

### 4. 处理器辅助（niki/api/_i18n.py）

```python
from niki.api._i18n import localized_error_response

raise HTTPException(
    status_code=400,
    detail=localized_error_response(
        request,
        code="INVALID_PHONE_FORMAT",
        key="auth.invalid_phone_format",
        fallback_message="手机号格式不正确",  # 兜底
    ),
)
```

- `request.state.lang`（middleware 设）→ 否则读 header → 否则 default
- `error` CODE 保持不变；只有 `message` 走翻译
- `fallback_message` 兼容未迁移的旧 handler；新加 key 时无须 fallback

### 5. 翻译键命名

- 点号分层：`{domain}.{code}`
- 当前覆盖的 domain：
  - `auth.*`        —— 登录、JWT、SMS、captcha、账户生命周期
  - `media.*`       —— 上传、缩略图、push 注册
  - `dashboard.*`   —— 报告模板、缺失字段
  - `auth_audit.*`  —— 审计查询
- 加新 key 时：`MESSAGES_ZH` 必填；`MESSAGES_EN` 必填；测试在
  `tests/i18n/test_translator.py` 里覆盖 zh + en 两个分支

### 6. 风险

| 风险 | 缓解 |
|------|------|
| 旧测试断言中文字面值 | 重构仅改 `message`，`error` CODE 与结构 100% 保留 |
| Accept-Language 解析慢 | O(N)，N ≤ 16，单 request 一次 |
| Thread safety | catalog dict 只读 + 单例创建期 `Lock` |
| 缺 key 导致空文案 | fallback 到 en，再 fallback 到 key，最后 fallback 到 handler 自带的 `fallback_message` |
| 客户端缓存脏 | `Vary: Accept-Language` 让 CDN 按语言分桶 |
| 翻译漂移（zh/en 不同步） | `tests/i18n/test_translator.py` 强制两个 catalog 都覆盖每个 key |
